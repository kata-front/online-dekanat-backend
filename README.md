# Online Dekanat Backend

Один JPEG, PNG или одностраничный PDF → локальный OCR → извлечение полей →
проверка комплектности → классификация вопроса.

Поддерживаются справка об обучении, заявление на академический отпуск и справка
о практике. Тип документа выбирается вручную. Классификатор выбирает маршрут
обработки вопроса; итоговый ответ студенту и экспорт `results.json` не реализованы.
Окончательное решение о принятии документа остаётся за сотрудником деканата.

## Установка

Команды выполняются из корня проекта, где находятся `main.py` и `models/`.

```bash
python -m venv .venv
```

Активация на Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

На Linux/macOS: `source .venv/bin/activate`.

### Tesseract

Для **Windows, CPython 3.14 x64** доступна сборка с нативными библиотеками:

```powershell
python -m pip install https://github.com/simonflueckiger/tesserocr-windows_build/releases/download/tesserocr-v2.11.0-tesseract-5.5.3/tesserocr-2.11.0-cp314-cp314-win_amd64.whl
```

Этот wheel не подходит для других версий Python. Для них нужна соответствующая
сборка из релизов tesserocr-windows_build. Уже установленную сборку повторно
скачивать не требуется.

На **Linux** сначала можно установить готовый wheel из PyPI. Если требуется
сборка из исходников, для Debian/Ubuntu установите системные зависимости:

```bash
sudo apt-get update
sudo apt-get install -y build-essential python3-dev pkg-config libtesseract-dev libleptonica-dev
```

Нативная установка зависит от платформы. Текущая интеграция проверялась
на Linux / Python 3.13; чистая установка на всех платформах не проверена.

### Зависимости и модель вопросов

Для CPU установите соответствующую сборку PyTorch перед остальными зависимостями:

```bash
python -m pip install "torch==2.14.1" --index-url https://download.pytorch.org/whl/cpu
python -m pip install -r requirements.txt
python -m pip check
python -m services.question_model --download --warmup
```

Классификатор использует **Qwen/Qwen3-0.6B**, ревизия
`c1899de289a04d12100db370d81485cdf75e47ca`. Первичная загрузка требует доступа
к Hugging Face и около 1,2 ГБ для весов. Кеш — `models/llm`.
Для FP32 планируйте около 4 ГБ RAM на процесс. GPU не требуется.

При HTTP-запросах веса не скачиваются. Если локальные веса отсутствуют,
вопрос, требующий модели, завершится ошибкой `503`. Очевидные вопросы
обрабатываются правилами без загрузки модели. Значения полей документа
в модель не передаются — только вопрос и имена доступных полей.

Прогрев CLI проверяет установку, но не сохраняет модель в памяти будущего
процесса сервера. Сервер загружает локальные веса при первом вопросе,
которому действительно нужна нейросеть; этот запрос может быть медленнее.

Русская OCR-модель уже находится в `models/tessdata/rus.traineddata`:
`tesseract-ocr/tessdata_fast`, версия 4.1.0. EasyOCR не используется.
Внешних OCR/LLM API нет.

## Запуск

```bash
python -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Форма проверки API: http://127.0.0.1:8000/docs.

## API

### `GET /health`

Возвращает `{"status":"ok"}`. Это проверка доступности процесса,
а не готовности OCR или модели вопросов.

### `POST /analyze`

Вход — `multipart/form-data`:

- `photos`: ровно один JPEG, PNG или одностраничный PDF;
- `prompt`: непустой вопрос на русском языке, максимум 2000 символов;
- `document_type`: `study_certificate`, `academic_leave_application`
  или `internship_certificate`.

Ограничения: 10 МиБ на файл, 20 мегапикселей на изображение или рендер PDF.
PDF с паролем не поддерживается.

Ответ содержит:

| Ключ | Значение |
| --- | --- |
| `document_type` | Выбранный тип документа |
| `ocr_text` | Распознанный текст |
| `fields` | Извлечённые поля и графические отметки |
| `validation` | Результат `services/validation/service.py` |
| `classification` | Намерение вопроса и ключ запрашиваемого поля |

Пример классификации для вопроса «Как зовут студента?»:

```json
{"intent":"field","field":"student_name"}
```

Допустимые намерения:

- `field`: одно конкретное поле; `field` — ключ из карточки документа;
- `validation`: комплектность документа; `field=null`;
- `decision`: кто принимает окончательное решение; `field=null`;
- `unsupported`: неизвестная политика, неоднозначный или многополевой запрос;
  `field=null`.

Отсутствующее значение поля не меняет намерение: вопрос о незаполненной дате
остаётся `field`. Формирование ответа «не найдено» относится к следующему слою.
Модель не изменяет результат валидации и не решает, принят ли документ.
Допустимые JSON ограничены при генерации и проверяются Pydantic. Это гарантирует
структуру успешного результата, но не безошибочность понимания любого вопроса.

Даты возвращаются в формате `YYYY-MM-DD`, курс — строкой с целым числом,
текстовый пропуск — `"не найдено"`, подпись и печать — boolean.
В карточке академического отпуска поля печати нет.

Ошибки:

- `422`: некорректные параметры, файл или превышение токенного бюджета вопроса;
- `413`: превышение размера файла;
- `503`: ошибка OCR, отсутствующая/неисправная модель либо занятая очередь;
- `504`: превышение бюджета генерации классификации.

Внутренние подробности ошибок не возвращаются клиенту. Недоступность модели
не маскируется под `unsupported`. При заполнении очереди классификатора
возвращается `Retry-After: 1`.

## Настройки классификатора

| Переменная | Назначение |
| --- | --- |
| `QUESTION_MODEL_CACHE` | Каталог кеша весов, по умолчанию `models/llm` |
| `QUESTION_MODEL_PATH` | Локальный snapshot той же Qwen3-0.6B, не ID модели |
| `QUESTION_MODEL_THREADS` | CPU-потоки, по умолчанию до 4 |
| `QUESTION_MODEL_QUEUE_TIMEOUT` | Ожидание блокировки, по умолчанию 10 секунд |
| `QUESTION_MODEL_GENERATION_TIMEOUT` | Бюджет генерации, по умолчанию 20 секунд |

Генерация выполняется вне event loop, в ограниченном пуле. Таймаут проверяется
между шагами модели: отдельный forward pass не прерывается жёстко.

Проверка классификатора из командной строки:

```bash
python -m services.question_model --self-test
python -m services.question_model --question "Когда выдали справку?" --document-type study_certificate
```

## Тесты

Существующие unit-тесты заменяют Tesseract и OCR. Они проверяют загрузчик,
поля, даты, графические эвристики и API; качество настоящего OCR не измеряют.
Неопределённый запрос «Вопрос» обрабатывается без загрузки модели.

```bash
python -m pip install -r requirements-test.txt
python -m pytest
ruff check .
ruff format --check .
```

В `tests/test_api.py` два теста всё ещё требуют прежний набор ключей ответа
(`document_type`, `fields`). До их актуализации общий прогон завершается ошибкой:
текущий контракт дополнительно содержит `ocr_text`, `validation`, `classification`.
Есть замечания Ruff в существующих файлах валидации, API и ручном скрипте модели.

Текущий `/analyze` отдельно проверен настоящим Tesseract на `open-001.pdf`
и `open-005.pdf`: поля и валидация совпали с учебным эталоном. Это не полный
OCR-бенчмарк набора и не гарантия качества на произвольных документах.

## Ограничения

- Подпись и печать проверяются на наличие, не на подлинность. Графические
  эвристики рассчитаны на учебные макеты, поля извлекаются регулярными выражениями.
- Валидация ожидает полный набор ключей и маркер текстового пропуска
  `"не найдено"`. Отсутствующие ключи, пустые строки, `None` и подчёркивания
  дополнительно не нормализуются. Эти случаи требуют отдельной доработки.
- OCR вызывается один раз на документ и выполняется в рабочем потоке.
  Общего лимита тела до multipart-разбора, отдельной ограниченной OCR-очереди,
  общего таймаута запроса, авторизации и rate limiting нет. Для публичного
  размещения эти ограничения нужно обеспечить отдельно.
- Файлы закрываются после обработки и не сохраняются приложением постоянно.
- Итоговый ответ с источниками, экспорт `results.json` и решение о принятии
  документа не входят в классификацию вопроса.
